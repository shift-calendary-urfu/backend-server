# Регламент работы с Git и ветками в проекте
Соблюдайте, пожалуйства, правила. Особенно важно: 2.1, 2.2
## 1. Структура и назначение веток
В репозитории используется фиксированная структура веток. Создание веток, не соответствующих правилам именования, запрещено.

- `main` (Главная ветка)

* Статус: Стабильный production-код.
   * Правило: Категорически запрещено делать прямые коммиты или мержить свои ветки напрямую в main. Сюда код попадает только из ветки dev при выпуске официального релиза.
     
- `dev` (Основная ветка разработки)
  
* Статус: Среда для сборки всех готовых фич и тестов.
   * Правило: Основная ветка для интеграции. Все разработанные фичи и написанные тесты мержатся только в dev через Pull Request. Прямые коммиты в dev запрещены.

- `feature-<name>` (Ветки для разработки функционала)

* Правило: Создаются строго от ветки dev. Название должно отражать суть фичи (например: feature-billing-stripe, feature-auth-jwt).
   * Куда мержится: Обратно в dev.

- `test-<name>` (Ветки для написания тестов)

* Правило: Создаются от ветки dev или от конкретной ветки фичи, если тесты пишутся параллельно. Название должно отражать, что именно тестируется (например: test-api-endpoints, test-database-queries).
   * Куда мержится: В ветку dev (или в родительскую фичу).

## 2. Пошаговый рабочий процесс (Workflow)
## Шаг 2.1. Начало работы
Перед созданием ветки всегда обновляйте локальный dev, чтобы не плодить конфликты:
```
git checkout dev
git pull origin dev
```
Создайте свою ветку от обновленного dev:

# Для разработки фичи
```
git checkout -b feature-my-awesome-feature
```
# Для написания тестов
```
git checkout -b test-my-new-tests
```

## Шаг 2.2. Разработка и коммиты
Пишите код, делайте коммиты. Перед отправкой ветки в удаленный репозиторий, убедитесь, что вы не отстали от dev:
```
git fetch origin
git merge origin/dev# Если возникли конфликты — исправляйте их локально в своей ветке!
```

## 3. Тотальная самопроверка перед мержем
У нас нет выделенного ревьюера, который будет подчищать за вами ошибки. Вся ответственность за работоспособность кода лежит исключительно на авторе.
Перед тем как нажать кнопку Merge в Pull Request, вы обязаны перепроверить свой код 100 раз.
Что значит «перепроверить 100 раз» на практике:

   1. Локальный запуск: Проект с вашими изменениями компилируется, запускается и стабильно работает локально. Ничего не падает.
   2. Анализ Diff (разницы кода): Откройте вкладку Files changed в вашем Pull Request на GitHub и лично строчка за строчкой перечитайте весь свой код.
   3. Удаление мусора: Убедитесь, что в коде не осталось забытых console.log, закомментированных кусков старого кода, временных заглушек или отладочных данных.
   4. Проверка логики: Задайте себе вопрос: «Сломает ли этот код существующий функционал? Учел ли я крайние случаи (edge cases) и ошибки авторизации/запросов?».

Только когда вы абсолютно уверены, что код идеален, его можно вливать в dev.
